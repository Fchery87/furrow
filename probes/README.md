The first proof has two parts. Python checks the schedule. REAPER has to check the sound.

**Checked on this machine.** `python3 probes/check_schedule.py` checks the half-sample tie, the 120 BPM step and half-step gate, the full and partial ramp integrals, the 38 events of the 4 by 16 pattern, and the one-sample diff. `python3 probes/check_lua_scripts.py` runs both Lua scripts against a stub REAPER API under Lua 5.4. It needs `pip install lupa` and skips without it. The stub shows what the scripts ask REAPER to do. It does not show that REAPER honours it. `probes/expected/constant-120.txt` is the file a capture compares against. `probes/expected/ramp-44100-1024.txt` uses the map in `probes/cases/ramp-44100-1024.txt`, with BPM linear in time as REAPER 7.82 played it.

1. Copy both files from `jsfx/` into the REAPER Effects directory.
2. Run `lua/furrow_probe_layout.lua` once. It gives each receiver its own slot. A second run finds the named tracks and stops. Remove those tracks before creating the layout again. If a JSFX fails to load, the script removes what it created and says which file is missing.
3. Set 44.1 kHz, 1,024-sample blocks, and a constant 120 BPM. Play from beat 0 through the sixteen steps, then stop. Starting playback clears the previous capture.
4. Run `lua/furrow_probe_dump.lua`. It writes three files next to the saved project, or into the REAPER resource directory for an unsaved project. The console lists the paths.
5. Run `python3 probes/diff_log.py probes/expected/constant-120.txt furrow-capture-events.txt`.
6. Repeat with the ramp case. `furrow-capture-tempo-block.txt` holds the tempo read in `@block`. `furrow-capture-tempo-sample.txt` holds the tempo read in `@sample`, one line per played sample.

**gmem layout, version 2.** Named gmem `FurrowProbeReceiver`. `gmem[0]` is the layout version. `gmem[2]` and `gmem[3]` count block and sample tempo entries. `gmem[4]` is the project sample of the first sample tempo. `gmem[10 + slot]` counts slot events. Block tempo pairs start at 1,000. Sample tempos start at 200,000. Slot events start at 2,000,000 + slot × 500,000, nine numbers each. Sample, order, lane, bus, destination bus, channel, note, velocity, kind. Kind 1 is a note-on. Kind 0 is a note-off. Sample positions come from `play_position` in each block, so they count from project time zero.

**Known limits.** REAPER 7.82 reports `tempo` once per block, at its first sample. The engine assumes the previous block's tempo change continues through the current block and converts beats with that ramp. With the engine that held one tempo per block, the ramp capture missed the one-sample target by one sample on one event. See `probes/results/reaper-7.82-linux/README.md`. A model of the extrapolating engine, run against that capture's block tempos, puts all 38 ramp events on the exact sample. A REAPER capture still has to confirm it. The block where a ramp starts or ends is the weakest case, because the previous block's change is the wrong guess there. The [ReaScript reference](https://www.reaper.fm/sdk/reascript/reascripthelp.html) documents the `I_MIDIFLAGS` source bus in bits 14 to 21 and the destination bus in bits 22 to 29, where 0 means all and 1 means the normal bus. The layout selects bus 1 for both. A capture still has to show that the host honours it. The receiver stores `midi_bus` on every event so the capture can show what arrived. The receiver declares stereo pins so that `@sample` has audio to run on.
